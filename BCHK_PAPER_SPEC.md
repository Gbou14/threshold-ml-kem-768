# BCHK+ Threshold KEM — algorithm specification extracted from the paper

Source: Oleksandra Lapiha and Thomas Prest, "A Lattice-Based IND-CCA Threshold
KEM from the BCHK+ Transform," Asiacrypt 2025, [eprint 2025/1958](https://eprint.iacr.org/2025/1958.pdf)
(42 pages, read in full for this extraction). This document transcribes the
concrete construction as precisely as PDF-text-extraction allows, for use as
an implementation reference. Where notation could not be rendered exactly,
`[UNCLEAR: ...]` flags the spot.

This is a companion to `FO_REDESIGN_CONTEXT.md` (why this paper was chosen)
and this repo's `src/kyber/README.md` "Phase 5" section (the FO-threshold
problem this paper avoids). Read those first if you haven't.

---

## 0. One-paragraph summary of the whole construction

BCHK+ = BCHK transform (CCA security from a one-time-signature-bound
identity-based encryption, no thresholdization of the CCA check needed) +
FO transform (only for *decapsulation consistency*, applied to the already
recovered, non-sensitive plaintext, so it also doesn't need thresholdizing).
Concretely: `Encaps` samples a message `msg`, generates a **fresh one-time
WOTS+ keypair** `(sk,vk)` per encapsulation, derives ciphertext randomness
`rand = G_fo(msg)`, encrypts `msg` under a lattice threshold-IBE (TIBE)
using `id = vk` as the IBE identity, and signs the resulting IBE ciphertext
with `sk` under `vk`. The TKEM ciphertext is `(ct, vk, sig)`. Any `T` of `N`
shareholders can jointly decrypt (via a 3-round `ShareExtract`/`Combine`
TIBE protocol below) *without ever reconstructing the TIBE master secret*,
recovering `msg`; the coordinator then re-derives `rand`, re-encrypts, and
checks it equals `ct` (the FO part) before releasing the shared secret
`K = H_fo(msg||ct)`. **There is no threshold signing anywhere in this
scheme** — the one-time signature is generated by whoever runs `Encaps`
(the party creating the ciphertext, e.g. the coordinator), not by the
shareholders; "Plover"/"Threshold Raccoon" are cited as *inspiration* for
the noise-flooding + 3-round masking techniques used inside the TIBE's
threshold decryption, not as an actual signature scheme in use here. The
actual one-time signature scheme instantiated is **WOTS+** (hash-based,
Appendix A), not Plover/Raccoon.

## 1. Parameters and notation

**Ring**: `R = Z[X]/(X^d + 1)`, a power-of-two cyclotomic ring of degree
`d`. `R_q = R/qR`. `q` is chosen prime with `q = 5 mod 8` (per Lemma 1),
which guarantees `R_q` is isomorphic to a direct product of two fields of
order `q^{d/2}`, i.e. `R_q ~ F_{d/2} x F_{d/2}` — this splitting is required
for the identity-embedding map (Section 4.2 below) to work.

**Concrete parameter set (Table 2, the paper's only instantiated set)**:

| Symbol | Meaning | Value |
|---|---|---|
| `κ` | security parameter (bits) | 128 |
| `T` | decryption threshold | 32 |
| `Q_Dec` | bound on adversary's decryption/ShareDecaps queries (proof parameter, not a hard protocol limit) | 2^40 |
| `q` | ring modulus | ~2^100 (prime, `q = 5 mod 8`) |
| `d` | ring degree | 4096 |
| `β` | offset constant in `A0`'s construction / `Decomp_β` parameter | 2^77 |
| `ς_a` | Gaussian width for `(s_a, e_a)` (the actual TIBE master secret) | 8 |
| `ς` | Gaussian width for TIBE encryption randomness `s`, `e`, `e'` | 4 |
| `ς_p` | Gaussian width for per-shareholder blinding `(x_{i,0}, x_{i,1}, p_i)` (noise flooding) | 2^47 |
| `ς_RLWE` | Gaussian width used in the proof's trapdoor-embedding matrix `R` | 4 |
| `|ek|` | encryption-key size | 50 KiB |
| `|ct|` | TKEM ciphertext size (`ct, vk, sig` together) | 450 KiB |

**N is not fixed in the table** — the paper states sizes are "essentially
constant in T" (and doesn't depend on N at all), so N is a free protocol
parameter (number of shareholders); only T (how many must cooperate) drives
parameter sizing, via `Q_Dec` and the correctness bound. **Open question for
us**: no guidance on how small T can be pushed down from 32 while keeping
these exact `ς`/`q`/`d` values valid — Section 7 sketches how each term
scales but doesn't give a second table. See Section 7 open questions below.

For comparison, current repo's ML-KEM-768: `d=256`-degree polynomial ring
(k=3 module rank instead), `q=3329` (~12 bits), ciphertext ~1088 bytes. This
paper's parameters are dramatically larger: `d=4096` (16x), `q~2^100` (~8x
more bits per coefficient), ciphertext 450 KiB (~400x larger). This is the
concrete cost of threshold-CCA-with-no-MPC/FHE.

**Notation carried through the algorithms below**:
- `[[x]]_i` — party `i`'s Shamir share of value `x` (secret-shared
  coefficient-wise over `Z_q`, standard `(T,S)`-Shamir sharing per Section
  2.1: a degree-`<T` polynomial `P` with `P(0)=x`, share for party at
  evaluation point `s` is `P(s)`; reconstruction via Lagrange interpolation
  `a = Σ_{s∈S} λ_{s,S} · [[a]]_s`).
- `λ_{i,act}` — the Lagrange coefficient for party `i` given the active set
  `act`.
- `D_{R,ς}` / `D_{R^k,ς}` — discrete Gaussian over the ring `R` (or `R^k`)
  with width parameter `ς`.
- `Decomp_β(x)` — for odd `q` and power-of-two `β`, decomposes
  `x = c0·β + c1` with `|c1| ≤ β/2`, `|c0| ≤ ⌈(q-1)/2β⌉`; extended
  coefficient-wise to ring/`R_q` elements.
- `H_cmt : R_q -> {0,1}^{2κ}`, `H_mask : {0,1}^* -> R_q^2` — random oracles
  used inside the TIBE's threshold-decryption protocol (commit-then-reveal
  and pairwise additive masking, respectively).
- `G_fo : {0,1}^* -> R` (or the encryption-randomness space), `H_fo :
  {0,1}^* -> K` (key space) — the two FO random oracles at the TKEM level.
- `E : S_vk -> R_q^x` — injective embedding of one-time-signature
  verification keys into *units* of `R_q` (Section 4.2 below); this is
  what plays "identity" in the BCHK-style transform.

## 2. The Coset-Hint-MLWE assumption

**Plain MLWE**: `(A, [A|I]·s)` is pseudorandom for `A ← R_q^{m×n}` uniform,
`s ∈ R^{n+m}` short.

**Hint-MLWE** (Kim et al., CRYPTO 2023; Definition 10 in the paper): same,
but the adversary additionally gets `ℓ` "hints" of the form
`(c_i, z_i = c_i·s + r_i)`, where `(c_i, r_i)` are drawn from an "adequate"
(short) distribution `P(s,e)` (Figure 2a):

```
for each hint i:
  u_i ← R_q
  (c0_i, c1_i) := Decomp_β(u_i)
  (p0_i, p1_i) ← D_{R^{n+m}, ς_p}
  z_i = [s;e]·c0_i + p_i
return {c_i = (c0_i,c1_i), z_i}_i
```
(`i.e. r_i` above `= p_i`, the noise added to mask the hint.) `ℓ=0` recovers
plain MLWE; `(ℓ,n)=(0,1)` recovers Ring-LWE.

**Coset-Hint-MLWE** (this paper's new assumption, Definition 11): *identical
setup*, except the noise term `p_{j,i}` in each hint is no longer sampled
from the full Gaussian over `R^{n+m}` — it's sampled from a **public coset**
`a_i + Λ ⊆ R^{n+m}` for a fixed lattice `Λ` and offset `a_i`. Concretely
(Figure 2b, `P_cond(S,E)`):

```
for each hint i:
  u_i ← R_q^m
  (c0_i, c1_i) := Decomp_β(u_i)
  (p_i, x_i) ← D_{Λ_q^{r_i - A0(B)·T·c_i}([A0(B)|A2]), ς_p}   -- coset-conditioned Gaussian
  z_i = T·c_i + p_i
return {c_i=(c0_i,c1_i), (z_i,x_i)}_i
```
where `A0(B) = [I_m | A | β·I_m − B]`, `T^T = [E^T S^T I_m; I_m 0 0]`, and
`(S,E)` play the role of the MLWE secret/error being hidden (in the actual
TKEM instantiation `n=m=1`, i.e. a *single* secret ring element pair
`(s_a,e_a)` — this is the TIBE master secret).

Intuition the paper gives: taking `Λ = R^{n+m}` (i.e. no coset restriction)
recovers plain Hint-MLWE exactly, so this is a genuine generalization. The
worry is that sampling from a sparser coset could leak more about the
secret than sampling from the whole space — **Theorem 1** shows this isn't
the case: given a `PPT` algorithm `TrapGen(κ)` producing `(A2, T_{A2})`
with `A2 · T_{A2} = 0 mod q` and `‖T_{A2}‖_GS ≤ B`, there's an efficient
reduction from Hint-MLWE to Coset-Hint-MLWE losing only a factor `m` in
advantage plus `ℓ·O(ε)` (proved via a 6-hybrid argument using a
`ModNTRU`-style trapdoor embedded in `A2`, `SamplePre`/`SamplePreMP`
preimage sampling algorithms, and the Leftover Hash Lemma). **This
trapdoor and the whole Coset-Hint-MLWE <= Hint-MLWE reduction is a proof
artifact — it is not needed to run the real protocol** (see the flag in
Section 7 below: `A2` in the actual `TIBE.Setup` is sampled uniformly at
random with no trapdoor at all).

## 3. Building blocks

### 3.1 The underlying IBE: Agrawal-Boneh-Boyen (ABB), noise-flooded

The paper starts from the ABB IBE (Agrawal-Boneh-Boyen, Eurocrypt 2010): a
valid identity secret key for identity `id` satisfies
`[A | B(id)] · sk_id = target` for a matrix `B(id)` that depends linearly
(via a gadget matrix) on the identity. The paper picks ABB specifically
*because* (unlike GPV-style IBEs where `A · sk_id = H(id)` — a trapdoor
purely for `A`) two identity keys `sk_id^1, sk_id^2` for the *same*
identity don't trivially combine into a short vector satisfying
`A·(sk_id^1-sk_id^2)=0`; only a trapdoor for the *joint* matrix `[A|B(id)]`
exists, which blocks a natural key-recovery attack that would otherwise
apply once you noise-flood/thresholdize (this is spelled out in Section
1.2 as the reason GPV-style IBEs were rejected).

The concrete instantiation is not "textbook ABB" but a specific variant
built for this paper (Section 4.2, Algorithms 1-4 below), converted to be
**threshold-friendly via noise flooding**: instead of a real Gaussian
trapdoor sampler run interactively by shareholders (expensive, hard to
thresholdize — this is exactly why GPV/ABB-style IBEs are "notoriously
difficult to thresholdise" per the paper's own framing), each shareholder
adds a large, statistically-hiding Gaussian blinding term (`ς_p = 2^47`,
astronomically larger than the actual secret's width `ς_a = 8`) to its
partial computation before revealing anything, then the *sum* of these
oversized blinding terms cancels out through the linear-algebra structure
of `Combine`. This is the "flood and submerge" technique credited to
Espitau-Niot-Prest (ref [30]) and used in threshold-Raccoon-style schemes.

### 3.2 Plover / Threshold Raccoon — role clarified

**Important correction to how I initially framed this task**: Plover and
the "TRaccoon^sel_{3-rnd}" variant of Threshold Raccoon are **not** used as
an actual signature scheme run by shareholders. They contribute two things
to the *threshold-decryption* (TIBE) protocol structure only:
1. The **noise-flooding technique itself** (Plover is a noise-flooded,
   threshold-friendly hash-and-sign signature; the paper borrows its
   flooding approach for TIBE decryption, not its signing).
2. The **3-round commit/reveal/combine protocol shape** (`ShareExtract_0`
   commits to a masked value, `ShareExtract_1` reveals it, `ShareExtract_2`
   uses the revealed values plus pairwise PRF masking to compute the final
   contribution) — this specific round structure is credited to
   `TRaccoon^sel_{3-rnd}` (del Pino et al., a threshold-signature paper),
   reused here for threshold *decryption*, not signing.

There is **no threshold signing protocol anywhere in this scheme.** The
one-time signature (`SIG` in the TKEM construction) is signed by a single
party — whoever runs `Encaps` — using a freshly generated keypair, exactly
once, and verified by every shareholder before they'll process a
decapsulation share. This is the actual signature scheme:

### 3.3 The one-time signature: WOTS+ (Appendix A, not Plover)

Concretely instantiated as **WOTS+** (Hülsing, Africacrypt 2013), a
hash-based one-time signature, with these parameters and hash-function
instantiation (Theorem 6): `n=256`, Winternitz parameter `w=16`, `κ=128`:

```
f_k(x)      = SHA2-256( toByte(0,32) || k || x )
PRF_seed(y) = SHA2-256( toByte(1,32) || seed || y )
H_msg(m)    = SHA2-256( toByte(2,32) || m )
H_key(k)    = SHA2-256( toByte(3,32) || k )
```

giving `ε-sEU-CMA` security with `ε = 2^-128` (the paper computes 2^-110
via [37]'s bound but conservatively assumes 2^-128, Remark 9), and a
**signature length of 2144 bytes**.

Full WOTS+ definition (Definition 12, Figure 6):
- Let `l1 = ⌈n/log w⌉`, `l2 = ⌊log(l1·(w-1))/log w⌋ + 1`, `l = l1+l2`.
- Chaining function `c^i_k(x,r)` for `r=(r_0,...,r_{j-1})`: `c^0_k(x,r)=x`;
  `c^i_k(x,r) = f_k(c^{i-1}_k(x,r) xor r_i)` for `i>0`.
- `WOTS.Keygen(1^κ)`: `sk = (sk_1,...,sk_l) ← {0,1}^{n×l}`, `seed ←
  {0,1}^{2κ}`, `vk_1 = H_key({c_k^{w-1}(sk_i,r)}_{i=1}^l)`. Return `(sk, vk=
  (seed, vk_1))`.
- `WOTS.Sign(sk,vk,msg)`: `m = H_msg(msg)`; `Decomp_w(m) = (m_1,...,m_{l1})`
  (base-`w` digits); `chk = Σ_i (w-1-m_i)`; `Decomp_w(chk) = (chk_1,...,
  chk_{l2})`; `B=(b_1,...,b_l) = m||chk`; `(r,k) ← {PRF_seed(i)}_{i=1}^{2(w-1)}`;
  `sig = (c_k^{b_i}(sk_i,r))_{i=1}^l`.
- `WOTS.Verify(vk,msg,sig)`: recompute `B` as above, check
  `vk_1 = H_key({c_k^{w-1-b_i}[b_i+1,w-1]}(sig_i,r))_{i=1}^l`.

### 3.4 The composition — what plays "identity" and what's signed

- **Identity = one-time verification key `vk`** (embedded into `R_q^x` via
  `E`, Section 4.2). A fresh `(sk,vk)` pair is generated *per Encaps call*.
- **What's signed**: the TIBE ciphertext `ct` (the raw `(u,v)` pair from
  `TIBE.Encrypt`), under the fresh `sk`, producing `sig`.
- **The TKEM ciphertext is the triple `(ct, vk, sig)`.**
- **Why this gives CCA without thresholdizing the check**: every
  `ShareDecaps`/`ShareExtract` call first asserts `SIG.Verify(vk,ct,sig)=1`
  — this check is on entirely **public** values (no secret material
  involved), so every shareholder can (and must) run it locally with no
  MPC. An adversary who wants a decryption oracle answer for a *modified*
  ciphertext under someone else's `vk` cannot produce a valid `sig` for it
  (one-time signature unforgeability) — this is the classical
  Boneh-Canetti-Halevi-Katz argument, now applied per-shareholder instead
  of per-single-decrypter, and it's exactly what makes the *CCA* part
  threshold-free.

### 3.5 The identity-embedding map `E`

`S_vk` (the space of all valid WOTS+ verification keys, a bitstring of
fixed length) must map into **units** of `R_q`, injectively, such that any
two *distinct* verification keys map to elements whose *difference* is
also a unit — required so that `A1 - E(vk)·G` behaves as a fresh
trapdoor-free matrix per distinct identity in the security proof (Section
5, the reduction embeds a gadget trapdoor specifically at `vk*`, the
adversary's challenge identity, and needs every other `vk != vk*` to *not*
accidentally also carry a usable trapdoor).

Construction (Section 4.2, "Identity Embedding"): pick `R, q` such that
`R_q ~ F_{d/2} × F_{d/2}` (guaranteed by Lemma 1's `q ≡ 5 mod 8` condition)
via isomorphism `f : R_q -> F_{d/2}×F_{d/2}`. Require `|S_vk| < q^{d/2}`.
Pick *any* efficiently computable injection `E_F : S_vk -> F_{d/2} \ {0}`
(the paper suggests simply using the binary representation of `vk`'s bits,
interpreted as a field element — since `vk` is a fixed-length bitstring
from WOTS+ and `q^{d/2}` is astronomically larger, any reasonable injective
encoding works). Define `E(vk) := f^{-1}(E_F(vk), E_F(vk))` (same value
embedded into *both* field factors). Then for `vk0 != vk1`:
`E(vk0)-E(vk1) = f^{-1}(E_F(vk0)-E_F(vk1), E_F(vk0)-E_F(vk1))`, which is a
unit in `R_q` iff neither coordinate is zero in its field factor — true
since `E_F` is injective and both coordinates are equal (so both are
nonzero together, or the whole thing is trivially excluded by `vk0!=vk1`).

**Implementation note**: this requires (1) choosing `q ≡ 5 mod 8` and
using Lemma 1's factorization to build the ring-to-field-product
isomorphism `f` (this is the same kind of NTT-friendly-modulus reasoning
as Kyber, but a different specific condition — Kyber wants `q ≡ 1 mod 2n`
for full NTT splitting into degree-1 factors; here we want `q ≡ 5 mod 8`
for splitting into exactly *two* degree-`d/2` factors), and (2) a concrete
choice of `E_F` — the paper doesn't pin one down beyond "an arbitrary
efficient embedding... e.g. using binary representations of the
polynomial coefficients," so this is a real implementation decision (see
Section 7 open questions).

## 4. The full threshold KEM construction

Two layers: (A) the TIBE (Threshold Identity-Based Encryption) — Figures 4
and 5, Algorithms 1-8; (B) the TKEM (Threshold KEM) built on top via
BCHK+ — Figure 3. Definitions 2/3 (Section 2.2) give the generic
interfaces both instantiate:

- `TIBE = (Setup, Encrypt, {ShareExtract_r}_r, Combine)`
- `TKEM = (Keygen, Encaps, {ShareDecaps_r}_r, Combine)`

*Remark 1 from the paper (important for our architecture): `TIBE.Setup`
(resp. `TKEM.Keygen`) is run by a trusted authority which distributes keys
over a secure channel — this matches this repo's existing `dealer.c`
role exactly.* `ShareExtract`/`ShareDecaps` are run interactively among
shareholders (broadcast or all-to-single-party) — this matches the
existing `shareholder.c` / HTTP round-trip pattern, just now needing 3
rounds instead of the current single-shot `threshold_partial_decrypt`.

### 4.1 TIBE public parameters (Section 4.2, matrices)

```
A0 = [1  a0  b0] · d0,   d0,a0 ← R_q^x × R_q,  (s_a,e_a) ← D_{R^2,ς_a},
                          b0 = (a0·s_a + e_a) − β                      (6)
A1 ← R_q^3                                     (uniform, real protocol)
A2 = [1  a2  b2] · d2,   d2,a2,b2 ← R_q^x × R_q^2                      (7)
G  = [1  g  g^2],        g ≈ q^{1/3}  (Micciancio-Peikert gadget matrix) (8)
r  ← R_q                 (public target for preimage sampling)
```

**`(s_a, e_a)` is the TIBE master secret** — this is the value that gets
Shamir-shared across the `N` parties (`dk_i := ([[s_a]]_i, [[e_a]]_i)`, a
`(T,[N])`-sharing). Everything else in `ek` is public.

**Critical implementation simplification, confirmed by re-reading
Algorithm 1 closely: `A2` is sampled *uniformly at random* in the real
protocol — no trapdoor is generated or needed at runtime.** The
`TrapGenNTRU`/`ModNTRU` machinery (Section 2.5, Remark 3) is used
*exclusively inside the security-proof hybrids* (Section 5, Hyb_{1,2}
through Hyb_10) to let the *reduction* answer oracle queries — it has
nothing to do with what an honest dealer actually computes. This
significantly de-scopes the implementation: we do not need a Module-NTRU
trapdoor sampler at all for a working system, only for (hypothetically)
reproducing the security proof/reduction, which is out of scope for an
implementation project.

### 4.2 Encode/Decode (Algorithms 2-3)

```
Encode(msg=(b_0,...,b_{d-1}) ∈ {0,1}^d) -> M ∈ R_q:
    M = Σ_i b_i · ⌊q/2⌋ · X^i

Decode(M = Σ_i α_i X^i) -> msg ∈ {0,1}^d:
    msg = Σ_i [α_i]_q · X^i    (round each coefficient to nearest bit,
                                 i.e. standard LWE "compress-to-1-bit")
```
This is the standard Lindner-Peikert-style binary message encoding —
directly analogous to Kyber's `poly_frommsg`/`poly_tomsg`.

### 4.3 TIBE.Setup — Algorithm 1

```
Input: 1^κ.  Output: ek, {dk_i}_{i∈[N]}.
1: d0, a0 ← R_q^x × R_q
2: (s_a, e_a) ← D_{R^2, ς_a}
3: A0 := [1 a0 b0]·d0,  b0 = (a0·s_a+e_a) − β
4: A1 ← R_q^3
5: A2 := [1 a2 b2]·d2,  d2,a2,b2 ← R_q^x × R_q^2
6: G  := [1 g g^2],  g ≈ q^{1/3}
7: r ← R_q
8: ek := (A0, A1, A2, G, r)
9: for i in [N]: dk_i := ([[s_a]]_i, [[e_a]]_i)     ▷ (T,[N])-Shamir sharing
10: return ek, {dk_i}_{i∈[N]}
```

### 4.4 TIBE.Encrypt — Algorithm 4

```
Input: msg ∈ {0,1}^d, id=vk, ek.  Output: ct.
1: F_vk := [A0 | A1 − E(vk)·G | A2]           ▷ F_vk ∈ R_q^{1×9}
2: s ← D_{R^3, ς}
3: e ← D_{R^3, ς} × D_{R^3, ς'} × D_{R^3, ς}  ▷ e ∈ R_q^{1×9}
       [UNCLEAR: exact split of e's three ς-blocks vs which A0/A1/A2
       columns each corresponds to — the middle block uses a distinct
       width ς' visible only here; Table 2 doesn't separately list ς', so
       either ς'=ς or this is a proof-only quantity. Needs checking
       against the correctness-proof section (Theorem 5) which uses only
       ς and ς' together as `ς+ς'` — worth re-deriving from Equation (13)
       during implementation rather than guessing.]
4: e' ← D_{R, ς}
5: u := F_vk^T · s + e                         ▷ u ∈ R_q^9
6: v := r·s + e' + Encode(msg)
7: return ct := (u, v)
```
This is a **Lindner-Peikert-style ciphertext**: `u` is 9 ring elements (the
"A-part"), `v` is 1 ring element carrying the encoded message — directly
analogous in shape to Kyber's `(u,v)` IND-CPA ciphertext, just over a much
larger matrix (`F_vk` has 9 ring-element columns vs Kyber's `k=3`) and
modulus.

### 4.5 Threshold decryption — Algorithms 5, 6, 7, 8 (Figure 5)

**Round 0 — `TIBE.ShareExtract_0`** (each active shareholder `i`, given its
share `dk_i` and the ciphertext's identity `vk`):
```
1: (x_{i,0}, x_{i,1}, p_i) ← (D_{R^3, ς_p})^3      ▷ fresh, huge (ς_p=2^47)
                                                       blinding values
2: y_{i,0} = a0·p_{i,0} + p_{i,1} mod q
3: y_{i,1} = (A1 − E(vk)·G)·x_{i,0} mod q
4: y_{i,2} = A2·x_{i,1} mod q
5: w_i = y_{i,0} + y_{i,1} + y_{i,2}
6: cmt_i = H_cmt(w_i)
7: return contrib_{i,0} := cmt_i               ▷ COMMIT only — w_i itself
                                                   is NOT sent this round
```

**Round 1 — `TIBE.ShareExtract_1`**: trivial reveal.
```
1: return contrib_{i,1} := w_i
```

**Round 2 — `TIBE.ShareExtract_2`** (now everyone has all `{cmt_j, w_j}`
for `j ∈ act`):
```
1: assert ∀j ∈ act\{i}: H_cmt(w_j) = cmt_j      ▷ catch anyone who lied
                                                    in round 0
2: ctnt = act || ct || {cmt_j, w_j}_{j∈act}
3: m_i = Σ_{j∈act} H_mask(seed_{i→j}, ctnt) − Σ_{j∈act} H_mask(seed_{j→i}, ctnt)
                                                 ▷ pairwise masks that
                                                    cancel to 0 when
                                                    summed over all of act
4: w := Σ_{j∈act} w_j
5: (c0,c1) := Decomp_β( d0^{-1}·(r − w) )
6: z_{i,0} = p_{i,0} + c0·λ_{i,act}·[[e_a]]_i + m_{i,0}
7: z_{i,1} = p_{i,1} + c0·λ_{i,act}·[[s_a]]_i + m_{i,1}
8: z_{i,2} = p_{i,2}
9: return contrib_{i,2} := (z_i, x_{i,0}, x_{i,1})
```
The `m_i` pairwise-mask construction is the classic "secure aggregation"
trick (Bonawitz et al.-style): each ordered pair `(i,j)` in `act` shares a
PRF seed `seed_{i→j}`; party `i` adds `H_mask(seed_{i→j},·)` and subtracts
`H_mask(seed_{j→i},·)`; summing `m_i` over all `i ∈ act` telescopes to
exactly 0, so it doesn't perturb the final `Combine` sum but does hide each
individual `z_i` from anyone who only sees a subset of contributions.

**Combine — `TIBE.Combine`, Algorithm 8**:
```
1: z0 = Σ_{i∈act} z_{i,0} + c1
2: z1 = Σ_{i∈act} z_{i,1}
3: z2 = Σ_{i∈act} z_{i,2} + c0
4: x0 = Σ_{i∈act} x_{i,0}
5: x1 = Σ_{i∈act} x_{i,1}
6: F_vk := [A0 | A1 − E(vk)·G | A2]
7: assert F_vk · [z x0 x1]^T = r  AND  ‖[z x0 x1]‖_∞ < B
8: return msg := Decode( v − [z x0 x1]^T · u )
```
`[z x0 x1]` is a 9-coefficient-block vector (`z=(z0,z1,z2)` is 3 ring
elements, `x0`, `x1` are each 3-ring-element vectors — matching `F_vk`'s 9
columns and `u`'s 9 coordinates). Step 7's assertion is the correctness/
soundness check: the combined vector must be a genuinely short preimage of
`r` under `F_vk` (this is what makes step 8's decryption work, by the
same algebra as any dual-Regev/LP-style scheme: `v - <y,u> = r·s + e' +
Encode(msg) - <y, F_vk^T·s + e> = Encode(msg) + (e' - <y,e>)` once
`F_vk·y = r`, and the residual error is small enough that `Decode` rounds
it away).

**Why this is "linear/shareable" the way the FO_REDESIGN_CONTEXT.md
document said the current repo's plain PKE decryption is**: every
per-shareholder value (`y_{i,*}`, `z_{i,*}`) is an **additive** function of
that party's Shamir share of `(s_a,e_a)` plus locally-sampled blinding —
`Combine` is a pure **sum** across `act`, exactly analogous to how the
existing repo's `threshold_finish_decrypt` sums partial NTT-domain
decryptions. The novelty here is that the thing being additively combined
recovers `msg` **directly** (no separate FO re-encryption-of-secret-message
step needed to get a CCA-secure result) — the CCA property is already
baked in via the signature-bound identity, not bolted on after via a
message-dependent hash check the way plain FO does it.

### 4.6 The TKEM layer — BCHK+ transform (Figure 3, Section 4.1)

```
TKEM.Keygen(1^κ):
    ({dk_i}_{i∈[N]}, ek) ← TIBE.Setup(1^κ)
    return ({dk_i}_{i∈[N]}, ek)

TKEM.Encaps(ek):
    msg ← {0,1}^d
    rand = G_fo(msg)                         ▷ FO: derandomize encryption
    (sk, vk) ← SIG.Keygen(1^κ)                ▷ fresh WOTS+ keypair, EVERY call
    ct = TIBE.Encrypt(ek, id=vk, msg; rand)
    sig ← SIG.Sign(sk, ct)
    K = H_fo(msg || ct)
    return (ct, vk, sig), K

TKEM.ShareDecaps_j(dk_i, (ct,vk,sig)), j ≤ rounds(=3):
    assert SIG.Verify((vk, ct, sig)) = 1       ▷ THE BCHK check — public,
                                                   no thresholdization needed
    contrib_{i,j} = TIBE.ShareExtract_j(dk_i, id=vk, ...)
    return contrib_{i,j}

TKEM.Combine({contrib_{i,rounds}}_{i∈act}, (ct,vk,sig)):
    assert SIG.Verify((vk, ct, sig)) = 1
    msg = TIBE.Combine(ct, vk, act, {contrib_{i,r}}_i)
    rand = G_fo(msg)                          ▷ FO: re-derive randomness
    assert ct = TIBE.Encrypt(ek, vk, msg; rand)  ▷ FO: re-encryption check
                                                    — THIS is the whole
                                                    "avoid FO's threshold
                                                    problem" trick: msg is
                                                    already recovered and
                                                    public/non-sensitive
                                                    by this point
    K = H_fo(msg || ct)
    return K
```

The paper's Figure 3 highlights (in green, i.e. the actual *delta* vs
vanilla BCHK) exactly the four `G_fo`/`H_fo`/`assert ct=...` lines above —
everything else is the unmodified Boneh-Canetti-Halevi-Katz pattern. This
is the cleanest single artifact in the paper for understanding "what did
they actually add to BCHK": **one derandomization line in Encaps, one
re-derivation + equality-check line in Combine.** Both operate on `msg`,
which by the time `Combine` runs it, has already been safely, linearly
reconstructed by the (thresholded) TIBE layer — so this FO check runs
**locally, by whoever calls Combine, on data that is no longer secret**,
which is exactly the sentence quoted in FO_REDESIGN_CONTEXT.md ("the input
to FO re-encryption is no longer sensitive and does not need to be
thresholdised").

**Note**: `TKEM.Combine` is written above as a single un-indexed step (no
per-shareholder role) — the coordinator role (matching the existing repo's
`coordinator.c`) runs this after collecting all three rounds' worth of
`contrib` from a `T`-sized `act`.

### 4.7 Correctness sketch (Theorem 5 + its proof, pages 27-28)

For honest ciphertext + honest shares, `Combine` computes
`y=(z0,z1,z2,x0,x1)` where (using the linearity of Shamir reconstruction
and the pairwise-mask telescoping):
```
z0 = c0·s_a + c1 + Σ_{j∈act} p_{j,0}
z1 = c0·e_a       + Σ_{j∈act} p_{j,1}
z2 = c0           + Σ_{j∈act} p_{j,2}
x  = Σ_{j∈act} x_j
```
Bounding `‖z0‖_∞, ‖z1‖_∞ ≤ d·ς_a·√d·⌈(q-1)/2β⌉ + β/2 + ς_p·√(Td) =: B`
(triangle inequality + Gaussian tail bounds, Lemmas 2-4), and similarly
bounding the final decoding error
`‖v − u^T·y − Encode(msg)‖_∞ ≤ ς√d + 3d√d·(ςB + (ς+ς')ς_p√(Td)) ≤ q/4`
(Equation 13) is sufficient for `Decode` to round correctly with
probability `1 - O(d·e^{-πd})`. **The `T` dependence enters only through
the `√(Td)` blinding-noise-accumulation term** — this is why threshold
size `T` (not `N`) drives the parameter table.

### 4.8 Decapsulation Consistency (Lemma 14 + Lemma 16)

`Adv_CD ≤ Q_{G_fo}·(Q_{G_fo}-1)/2 · 2^{-γ}`, where `γ` is the min-entropy
of an honest ciphertext (`Lemma 16: γ = log(ς^{7d}·ς'^{3d}·(1-ε)^{10})`,
i.e. it's essentially the entropy contributed by the `s,e,e'` sampled at
encryption time). Intuition: two different `act`/`act'` subsets could only
ever decrypt the *same* ciphertext to two *different* valid messages
`msg_0 != msg_1` if `TIBE.Encrypt(ek,vk,msg_0;G_fo(msg_0)) =
TIBE.Encrypt(ek,vk,msg_1;G_fo(msg_1))` — a birthday-bound collision in the
(high-entropy) ciphertext space, bounded by the query budget to `G_fo`
squared over `2^γ`. This is a purely combinatorial/statistical argument
over public quantities — again, no MPC/thresholdization needed, which is
the entire point of doing FO *here* instead of on the pre-FO sensitive
message the way naive threshold-ML-KEM does.

## 5. Security claims

- **IND-CCA2, selective-ID** (not adaptive): the adversary must commit to
  the challenge identity `vk*` and the corrupted-party set `cor`
  (`|cor|=T-1`, i.e. one below threshold) *before* seeing `ek`/public
  parameters (Definition 5, Figure 1). In practice this is largely
  academic for us: real usage always generates a *fresh* `vk` per
  `Encaps` call, so there's no meaningful sense in which a real adversary
  "selects" the challenge identity in advance — selective security is a
  proof-technique artifact, standard for lattice IBEs of this style
  (ABB-based schemes are typically only provably selective-secure; fully
  adaptive lattice IBE constructions are a harder, separate research
  problem cited as [8] "Bendlin et al." in Related Works, at the cost of
  generic MPC for Gaussian sampling).
- **Trusted setup**: `TIBE.Setup`/`TKEM.Keygen` must be run by a trusted
  authority (Remark 1) — this generates the *entire* secret `(s_a,e_a)`
  in one place and Shamir-shares it out, exactly the "dealer" model this
  repo already has (`src/dealer.c`). There is no distributed key
  generation (DKG) in this paper — that would be a further research
  extension, not something to invent ourselves.
- **Robustness**: **explicitly not achieved** in this base paper (Table 1:
  "Robust: No" for both TIBE and TKEM rows). A malicious shareholder can
  always force `Combine` to output `⊥` (e.g., by lying in Round 0/1, which
  is at least *detected* via the commit-then-reveal + assertion in
  `ShareExtract_2` step 1 — so a cheating party is caught, but there's no
  mechanism to identify *which* value was wrong and route around it or
  recover; the whole `act` set's decryption attempt simply fails). The
  2026 follow-up paper (eprint 2026/021, not covered by this extraction)
  reportedly adds robustness via Vandermonde secret sharing at a reduced
  query bound.
- **Full CCA2 bound** (Theorem 4) is a sum of five hardness-assumption
  terms (`RLWE`, `ModNTRU`, `Hint-MLWE`, another `RLWE` instance) plus
  several negligible statistical/combinatorial correction terms — see
  page 27 for the exact expression if a formal writeup ever needs it
  verbatim; not reproduced fully here since none of the coefficients are
  implementation-relevant (they matter only for choosing `κ,d,q` — already
  done for us in Table 2).

## 7. Open implementation questions

1. **Concrete instantiation of `H_cmt`, `H_mask`, `G_fo`, `H_fo`**: all
   four are specified only as random oracles with input/output types
   given, no concrete hash function pinned (unlike WOTS+, which gets an
   explicit SHA2-256-based instantiation in Theorem 6). Natural choice for
   this repo: SHAKE-128/256 (already used throughout `src/kyber/` for
   Kyber's own `G`/`H`/`PRF`/`XOF`), domain-separated by a prefix byte the
   way WOTS+'s own hash instantiation does above. This is a real design
   decision we'll need to make and document, not something the paper
   answers for us.

2. **Discrete Gaussian sampling over `R` at four different widths**
   (`ς_a=8`, `ς=4`, `ς_p=2^47`, `ς_RLWE=4` — the last is proof-only). This
   is a genuinely bigger implementation lift than Kyber's approach: Kyber
   deliberately avoids Gaussians in favor of the Centered Binomial
   Distribution (`η=2`) specifically because CBD is trivial to sample in
   constant time from raw random bytes, while a *true* discrete Gaussian
   sampler (needed here, especially for the huge `ς_p=2^47` blinding
   noise) is substantially more complex to implement correctly and in
   constant time (rejection sampling, cumulative-distribution-table
   methods, or convolution-based samplers are the standard options — each
   has real side-channel and precision-engineering pitfalls). This is
   probably the single largest new piece of cryptographic engineering
   this redesign requires that the existing Kyber code has no equivalent
   of at all.

3. **The ring-splitting isomorphism `f : R_q -> F_{d/2}×F_{d/2}`** (Lemma
   1, needed for the identity-embedding map `E`) needs an explicit
   algorithm, not just an existence proof. Lemma 1 gives the factorization
   `X^d+1 = Π_{i=1}^{k}(X^{d/k} - r_i) mod q` for the `k=2` case (i.e. `X^d
   + 1 = (X^{d/2}-r_1)(X^{d/2}-r_2) mod q`) — implementing `f` means: find
   concrete `r_1, r_2` for our chosen `d,q` (via Lemma 1's construction,
   itself citing [46, Corollary 1.2] — that reference's algorithm isn't
   reproduced in this paper and would need separate lookup), then
   implement the CRT-style map between "polynomial mod `X^d+1`" and "pair
   of polynomials mod `(X^{d/2}-r_1)`, `(X^{d/2}-r_2)`" representations.

4. **Concrete choice of `E_F : S_vk -> F_{d/2}\{0}`** (the embedding of
   WOTS+ verification keys into one of the two field factors) — the paper
   only says "an arbitrary efficient embedding... e.g. using binary
   representations of the polynomial coefficients." A WOTS+ `vk` here is
   `(seed ∈ {0,1}^{256}, vk_1 ∈ {0,1}^{256})` (n=256 per Theorem 6) = 512
   bits total; `F_{d/2}` for `d=4096` is a field of order `q^{2048}` with
   `q~2^100`, i.e. roughly `2^{204800}`-sized — vastly larger than the
   512-bit input space, so any reasonable fixed injective encoding (e.g.
   hash `vk` with a domain-separated XOF into enough field-element
   coefficients, reduced mod the field's defining polynomial) satisfies
   the requirement. Needs a concrete decision, but is low-risk (any
   collision-resistant encoding works — collisions would only matter if
   they *coincidentally* also produced a non-unit difference, an
   independently-negligible event given `|S_vk| ≪ q^{d/2}`).

5. **`Decomp_β` and the `d0^{-1}` inverse used in `ShareExtract_2` step 5**
   require `d0` to be an invertible element of `R_q` — `TIBE.Setup` already
   samples `d0 ← R_q^x` (the unit group) so this is fine, but computing
   inverses in `R_q` for a degree-4096, ~100-bit-modulus ring is a real
   (if standard, e.g. via the ring's NTT-split representation once split
   into the `F_{d/2}×F_{d/2}` factors from point 3 above, inversion
   reduces to per-factor field inversion) implementation task with no
   direct analogue in the existing Kyber code (Kyber never needs to invert
   ring elements).

6. **The `e ← D_{R^3,ς} × D_{R^3,ς'} × D_{R^3,ς}` split in `TIBE.Encrypt`
   step 3** — flagged inline in Section 4.4 above — the value `ς'` is used
   nowhere else explicitly defined in the parameter table; it appears
   again in the correctness bound (Equation 13, as `(ς+ς')`) and in the
   Section 5 proof (`ς' > 2√6·d·ς_RLWE·ς`, Equation 10) — so `ς'` *is*
   pinned by Equation (10) once `ς` and `ς_RLWE` are fixed
   (`ς'=4 => ς' > 2√6·4096·4·4`, which is enormous — this suggests `ς'` in
   Table 2's column might actually be reporting `ς_RLWE` and the *real*
   `ς'` for encryption noise is a separately-derived, much larger value we
   need to compute from Equation 10 rather than read off the table
   directly). **This needs to be worked out carefully during
   implementation, re-deriving from Equation (10)/(13) rather than
   assumed** — it's the one place the concrete-parameters table doesn't
   obviously give us a directly-usable number for every symbol used in
   the algorithms.

7. **Number of parties `N`** is never fixed by the paper (only `T=32` is
   instantiated) — we get to choose `N ≥ T` freely; parameter sizes don't
   depend on it. Reasonable to keep this repo's existing `N=5` demo
   topology in spirit but note `T=32 > N=5` from the existing demo, so the
   demo's `(N,T)` will need to grow substantially (e.g. `N=40, T=32` or
   similar) to match this paper's validated parameter regime, or we
   accept a smaller `T` and re-derive whether Table 2's `ς`/`q`/`d` values
   still satisfy the correctness/security inequalities (9)-(13) for a
   smaller `T` — this is a legitimate design choice for us, not something
   the paper mandates.

8. **No test vectors exist anywhere for this scheme** (unlike Kyber, which
   has the pq-crystals reference implementation this repo validated
   against byte-exact throughout Phases 1-5b) — there is no public
   reference implementation of BCHK+ TKEM to diff against. Validation will
   have to be entirely by internal consistency (round-trip correctness,
   the `T`-of-`N` vs below-`T` threshold behavior, and independent
   re-derivation of intermediate values from the algorithm boxes above),
   the same fallback methodology already used in this repo's Phase 3/5b
   for the parts of the existing threshold-Kyber system with no external
   reference either.
